      Context

      The failure mode nobody's CI catches

      An AI coding agent opens a pull request. The description says it implemented three things. The diff implements two.

      Nothing crashes. Tests pass, because the missing piece had no test. A reviewer skims a clean-looking diff, reads a confident summary, and merges. The omission surfaces three weeks later as a bug report nobody traces back to that PR.

      The checkmarks are the agent's claims, not verification. Every test passes.

      This is the dominant failure class in agentic coding, and the literature has converged on it from several directions. SWE-Compass, clustering 600 error traces per model, found requirement misinterpretation (30–34%) and incomplete solutions with side effects (29–42%) together accounting for over 60% of failures, while technical knowledge gaps sat at 5–8%. The bottleneck is not that models cannot code. It is that they do not finish what was asked.

      The most uncomfortable result comes from the false-success literature. In one study, 75.8% of self-assessing coding-agent trajectories that made explicit completion claims were false successes, and no LLM judge configuration tested exceeded AUROC 0.65 at catching it.

      That number is what started this project. If agents fail silently, and the obvious fix of asking another model barely beats a weighted coin, then the question worth asking is whether a boring deterministic rule does better.

      It doesn't. Not overall. That turned out to be the most useful thing I learned.

      Method

      What the benchmark contains

      310 synthetic instances derived from merged commits across eight mature Python repositories: attrs, click, flask, httpx, itsdangerous, jinja, requests and werkzeug. 13,104 records, 2,184 requirements scored per detector, base rate 27.9% omitted.

      The taxonomy is not arbitrary. Published taxonomies of unimplemented requirements split along the same lines, with missing component or feature at 32.4% and incomplete implementation at 18.1%. Absent is the missing component. Stub is the incomplete implementation. Unwired is the sneakiest of the three: the code exists, the symbol resolves, imports succeed, and nothing ever invokes it.
      
    
      
  
      

  
      
    
      Method
      
    
      
      
      The protocol, which mattered more than the code
      
      
      Six rules were frozen before a single number was measured. In hindsight these are the actual contribution. The detector is two hundred lines of AST walking, and the protocol is what makes its numbers mean anything.
      
      
        
        
      1. The detector never sees the gold patch
        SWE-bench's most-cited weakness. Independent audits found 32.67% of successful patches involved solution leakage, and a further 31.08% passed on inadequate tests. Runtime canary tests enforce the boundary.
        2. 
        
      2. Measure once, never tune afterwards
        If the bar is not cleared, write the null result. Do not adjust the corpus, the threshold or the prompt to improve the number.
        3. 
        
      3. MCC is the headline metric, not F1
        At a 27.9% base rate, F1 flatters classifiers that spray positives. MCC only scores high when a classifier performs across all four confusion-matrix cells. The first chart below lets you test this.
        4. 
        
      4. Cluster bootstrap intervals at instance level
        Requirements inside one instance share a repository, a commit and a specification. Row-level resampling would treat 2,184 correlated requirements as independent and produce intervals far tighter than the evidence supports.
        5. 
        
      5. Paired comparisons, not overlapping intervals
        Overlapping intervals do not establish that two detectors are indistinguishable. Every head-to-head claim is a paired difference on identical instances.
        6. 
        
      6. The pilot snapshot is frozen
        A week-two results file, never edited, with every later claim expressed as a delta from it.
        7.

      That result sits in the first screen of the repository README, not in a limitations appendix. Burying it would have been trivial: report F1 only, where 0.57 against 0.79 reads as a smaller gap, or report independent intervals and note that they overlap somewhat, or quietly drop the judge for being a paid dependency. Rule two exists to stop exactly that.
      
      
      What the deterministic rule does win is false positive rate, 0.043 against 0.113. That matters enormously for deployment and becomes the basis of the shipping decision. It is a different claim from "the deterministic approach is better", and conflating the two would have been dishonest.
      
    
      
  
      

  
      
    
      Finding 2
      
    
      
      
      Blind by construction, not by accident
      
      
      
        
      Recall by omission class
      Darker catches more, hatched catches nothing
      
        
      
      
      
      
      The detector reaches 0.96 recall on absent symbols and exactly 0.00 on both unwired and stubbed code. This is not a tuning failure. It asks one question, whether this symbol is defined in this file, and a stubbed function is still defined. So is an unwired one. The rule answers its question correctly and the question is insufficient for two of three classes.
      
      
      Publishing the per-class breakdown rather than the aggregate is the difference between a benchmark and a marketing number. A clean report means no symbols are entirely missing, not that nothing was omitted. That constraint later became a mandatory disclaimer inside the shipped tool's own output.

      Finding 5
      
    
      
      
      The extraction tax
      
      
      This is the finding that matters, and it came from asking an uncomfortable question about my own benchmark.
      
      
      Every number above depends on a hidden assumption: the requirement list is derived from the gold patch. The detector never sees that patch, but the requirements it checks against were computed from it. That is a perfect-extraction oracle, which makes every result an upper bound.
      

      

      
      In deployment nobody hands you the gold patch. So I built an extractor that reads only the issue and commit text, enforced by its own leakage guard, and emits a structured list of symbols and paths.
      
      
      Two decisions were locked before measurement. Matching is purely structural, exact case-sensitive multiset comparison with no model anywhere in the scoring path, because using an LLM to judge LLM-extracted text reintroduces the noise this experiment exists to isolate. And two strictness levels are always reported together: symbol-only and path-qualified. I also wrote down a falsification condition first: if extraction F1 came out above 0.9, the finding would be that the tax is small.
      

      
      
        
      Extraction F1 never comes close to the bar
      Dashed line: 0.9 falsification bar
      
        
      
        
      00.250.50.751
      
        
      Symbol onlyPath qualified
      
      
      

      
      The output was not degenerate: 150 of 310 extractions were non-empty, there were no parse failures, and spot checks showed real inference rather than word-copying. Given a vague commit message the model correctly returned nothing. Given a message that named a symbol, it got the name right and the file wrong. Only two path-qualified hits occurred in the whole corpus, both on commit messages that spelled out a file path.

      The middle condition decomposes the failure. Once paths are corrected for symbol-matched items, precision recovers to 0.923, so when the model names the right symbol the verdict is trustworthy. But recall collapses to 0.020. The tax is dominated by the extractor rarely naming the right symbol at all, then compounded by path errors.
      
      
      The engineering conclusion is that requirement extraction, not omission detection, is the hard problem. A detector operating on free-text-derived requirements is not merely degraded. It is actively harmful. Total cost of establishing that: $0.057.
      
    
      
  
      

  
      
    
      Process
      
    
      
      
      The bug that would have been p-hacking if I'd stayed quiet
      
      
      A fix that moves your number from −0.898 to +0.006 is exactly the shape of a p-hack. Here is the order things actually happened in.
      
      
        
        
      1. Condition defined before any code ran
        Symbol identification only, with oracle paths substituted for symbol-matched items.
        2. 
        
      2. First run returns −0.898
        The number looked wrong. That, and not a pre-registered check, triggered the inspection.
        3. 
        
      3. Bug found
        Non-matching items were still scored with their broken paths, so the condition was dominated by the path noise it existed to isolate.
        4. 
        
      4. Fixed back to the written definition: +0.006
        Only items naming a real oracle symbol are included, as specified in step 1.
        5. 
        
      5. Headline row checked, unchanged
        The shipped-pipeline result, −0.935 with tp 38, fp 791, fn 571, tn 7, is byte-identical across the buggy run, the fixed run and an independent verification run.
        6. 
      
      
      
      
        Disclosure
        
      Was the fix justified independently of the result?
      
        
      
          
      For
      The fix restores the specification rather than inventing one. Scoring non-matching items was always outside the condition's written definition.
      
          
      For
      The headline number never moved. The fix touched only the diagnostic.
      
          
      Against
      I did not catch it by review. I caught it because −0.898 looked wrong. That ordering is worth stating plainly rather than dressing up.
      
        
      
      
      
      
      All three points are recorded permanently with both numbers and the full diff. When a fix moves a number in the direction you wanted, publish the sequence, not just the justification. Reviewers can evaluate a justification. Only you know the sequence, so only you can disclose it.
      
    
      
  
      

  
      
    
      Finding 6
      
    
      
      
      Shipping a gate that discloses its own uncertainty
      
      
      The final phase packaged the detector as a GitHub Action that comments on pull requests.
      

      

      
      
        Decision
        
      Why the higher-MCC judge doesn't ship
      
        
      
          
      Fails the bar
      The gate's acceptance criterion is precision at or above 0.80. The judge's precision is 0.74. Shipping it would mean overriding my own threshold because I preferred a different metric.
      
          
      Cost of noise
      One false positive costs seconds of attention. A thousand produce a team that scrolls past every comment the tool posts. A paid API call per pull request adds an operational dependency on top.
      
          
      What ships
      The deterministic rule, with a 0.043 false positive rate. Offline, reproducible and free per run.
      
          
      Trade-off
      It catches under half of all omissions, and it says so in every comment.

      Finding 7
      
    
      
      
      A model that ranks well and forecasts badly
      
      
      Added 23 September 2026.
      
      
      The judge that won Finding 1 hands back a bare label. A gate built on it has nothing to threshold and no way to say "not sure, ask a human". So I tried a different kind of model. TypeSafe's Jev is a "System One" model: you send it state and typed yes/no questions, and it returns a probability for each one in about 100 milliseconds. The vendor describes those probabilities as calibrated. Its public documentation gives no calibration numbers.
      
      
      This corpus is a good place to check that claim, because every requirement has a ground-truth label. Jev (B7) saw exactly the diff the mid-tier judge saw, under the same 6,000-token truncation, and was scored twice: as a judge, with paired MCC like every other detector, and as a forecaster, with Brier score, expected calibration error and a reliability table.
      

      
      Everything was fixed before the first call
      
      
      Two variants, one compound question per requirement and three split questions (defined, wired, real body) combined with a minimum. A 0.5 threshold. A 0.3 to 0.7 "ask a human" band, taken from TypeSafe's own docs. And a pass/fail rule for "calibrated": ECE at most 0.05, every well-populated bin within 0.10 of the diagonal, and positive skill over the base rate. All of it went into ASSUMPTIONS.md and was merged on GitHub before any real request, so the timestamp is not mine to edit. The question text is hash-locked by a test. The full sweep cost about 18 cents.
      

      
      
        
      Paired ΔMCC, Jev minus rival
      Left of zero, Jev loses
      
        
      
        
      −0.50+0.5
      
        
      Cluster bootstrap over 310 instances, paired on identical inputs. The split variant against the deterministic rule is the only interval that touches zero.
      
      
      

      
      Jev loses to the mid-tier judge in both variants, and the calibration claim is not supported on this task. All three calibration conditions fail for both variants. The split variant beats the compound one on every measure, which is what TypeSafe's advice against compound questions predicts, but it still ends up statistically tied with the deterministic rule rather than anywhere near the judge.
      

      
      
        
      Reliability: what Jev says against what happened
      On the diagonal means calibrated
      
        
      
        
      One compound question, hollowThree split questions, filledPerfect calibration
      
        
      Each point is one bin of predicted P(omitted). Point area follows the number of requirements in the bin. Hover or tap a point for its numbers.
      
        
      Show the bins as a table
      
      
      

      
      The failure has a clear shape. Nearly every point sits far below the diagonal, so Jev says "probably omitted" about code that is implemented. In the compound variant, 366 requirements landed in the bin where Jev's average P(omitted) was 0.84, and only 12% of them were actually omitted. That is the worst gap, 0.72. False positive rates follow directly: 0.691 for the compound variant and 0.500 for the split one, against 0.113 for the judge.
      
      
      The interesting part is that the order is mostly right. Taken as scores, Jev's outputs separate omitted from implemented requirements well, with AUROC 0.910 for the compound variant and 0.936 for the split one. Those numbers are not directly comparable with a hard-label judge's, whose AUROC collapses to a single operating point. What they do say is that the problem is where the probabilities sit, not how they are ranked. A threshold picked after looking would score much better, and that is exactly the move the pre-registration rules out. A properly recalibrated Jev, fitted on held-out data and reported under a new detector name, is future work, not a rescue for this result.
      
      
      For the use I had in mind, a Stop hook that refuses to let a coding agent claim "done", this settles it. In the split variant's confident range, outside the 0.3 to 0.7 band, Jev covers 69% of requirements and is wrong on 31% of them. A gate that is wrong on almost a third of its confident calls trains people to ignore it.
      

      
      What the mocks could not catch
      
      
      The harness passed every offline test before it met the real service. Four things still went wrong, and each is recorded in the assumptions log.
      
      
        
        
      • The interpreter changed the corpus. Python 3.14 implements PEP 758, which lets except A, B: parse without parentheses. Old Python 2 code like except BadSignature, e: suddenly became valid, and five Python 2 commits slipped into one repository's corpus, 35 instances instead of 30. Rebuilt under 3.12, it matched exactly. The run now refuses to start on 3.14.
        • 
        
      • A CDN blocked the default user agent. The first real request came back as Cloudflare error 1010, because Python's urllib announces itself by default and bot rules reject it. A local mock server has no Cloudflare in front of it.
        • 
        
      • One 520 was not retried. An origin error outside the retry list dropped one variant. It was retried after the fix, which fills a gap rather than re-rolling a result, since no answer had ever been produced.
        • 
        
      • Truncation made some inputs identical. In five variants the mutation falls past the 6,000-token cut, so the mutated diff is byte-identical to the clean one while the labels differ. Every judge, the winning one included, gets one of each pair wrong by construction. Two flask commits also turned out to be the same change. Both are documented, not excluded, because dropping cases after seeing results is the filtering this project exists to avoid.
        • 
      
      
    
      
  
      

  
      
    
      Limits
      
    
      
      
      What's still open
      
      
        
        
      • Unwired remains underpowered at n=19 against a target of 100. Documented as directional rather than conclusive. It does not block the gate, whose criterion is overall precision, but it is not resolved.
        • 
        
      • The extraction tax is measured only on synthetic data. With eight real instances and zero positives, the real corpus could not support the same analysis.
        • 
        
      • The precision margin is thin and its interval straddles the threshold. A modest corpus change could flip it. The gate is designed to suspend itself if that happens.
        • 
        
      • Jev was not recalibrated. Its scores rank well, so a calibration layer fitted on held-out data might make it usable. That would be a new detector, reported next to B7 rather than instead of it.
        • 
        
      • The corpus has a duplicate commit and five truncation-identical variants. Deduplicating by diff hash at build time, then re-running every detector, is the fix.
        • 
        
      • The gate has been verified, not adopted. One live demonstration on my own repository proves the mechanism works. It is not evidence of value in a real team's workflow.

      Advice
      
    
      
      
      What I'd tell someone starting something similar
      
      
      
        
      Write the falsification condition before the code.Every task here had one except the final packaging task, and that was the only one where I found myself uncertain what would count as failure.
      
        
      Pick the headline metric before seeing any numbers.Had I chosen afterwards, an F1 of 0.44 for a baseline that flags everything would have made a much more comfortable table.
      
        
      Match your interval structure to your data's dependence structure.Getting this wrong does not produce a wrong point estimate. It produces intervals that lie, invisibly.
      
        
      Build the ablation that could destroy your result.Finding 5 exists because I asked what my own benchmark assumed. It returned the most negative number in the project and the most useful one.
      
        
      Pin the interpreter, not just the dependencies.A stdlib-only project still changed its own corpus when Python moved from 3.12 to 3.14. The full-corpus alignment check caught it. A 20-instance spot check would not have.
      
        
      A tool that hides its own error bars will be trusted exactly once.For anything that posts into a developer's workflow, uncertainty belongs in the output, not the appendix.
